B · events/

5 dari 5 file tersedia · 64.213 baris

Semua file event berbagi struktur yang sama: pembungkus event_id + event_type + dua timestamp, lalu data aslinya tersembunyi di dalam objek payload. Struktur berlapis ini meniru format log nyata.

{
  "event_id":         "EVT-00036639",          ← kunci unik (tapi bisa terulang = duplikat)
  "event_type":       "RETURN_CLOSED",          ← jenis kejadian
  "occurred_at_utc":  "2026-08-22T01:10:00Z",  ← KAPAN kejadiannya  ← dipakai untuk analitik
  "ingested_at_utc":  "2026-08-22T09:10:00Z",  ← KAPAN diterima sistem (bisa jauh lebih lambat)
  "payload": { ...data inti di sini... }         ← nested, bukan di root
}

Dua timestamp, dua masalah

Kalau selisih ingested_at_utc − occurred_at_utc lebih dari 24 jam, event ditandai is_late = true. Dari seluruh data, 3.659 event terlambat:

File eventTotalTerlambat%
web_events.json30.0001.8076,0%
payment_events.json21.9151.2545,7%

return_events.json3.4401925,6%

Total62.2073.6595,9%

Event tetap diproses — hanya ditandai, karena membuangnya berarti menghilangkan transaksi sungguhan. Polanya konsisten: yang normal tiba dalam hitungan jam, yang terlambat tiba puluhan jam kemudian.

Masalah #3 — event terlambat dan timestamp tidak berurutan Dua gejala sekaligus. Pertama, 3.659 event tiba lebih dari 24 jam setelah kejadiannya. Kedua, urutan kedatangan event tidak kronologis — retur bisa tercatat received sebelum requested. Karena itu status tidak diambil dari "event terakhir", melainkan dari tahap tertinggi yang pernah dicapai (requested → received → closed).
Masalah #4 — timestamp dengan timezone berbeda Tidak semua occurred_at_utc memakai akhiran Z (UTC). Sebanyak 5.837 event tercatat dengan offset +07:00 (WIB) — sisa dari sistem sumber yang memakai waktu lokal Jakarta. Penanganan: semua timestamp di-cast ke timestamptz di Silver, sehingga PostgreSQL menormalkannya ke UTC secara otomatis. Tanggal bisnis juga dihitung dengan AT TIME ZONE 'UTC' secara eksplisit, jadi tidak bergantung setelan server.
